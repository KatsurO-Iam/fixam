# Contributing to Fixam

Спасибо за интерес к Fixam!

Fixam — проект, который развивается как полноценный программный продукт. Чтобы разработка оставалась понятной, стабильной и удобной для всех участников, мы придерживаемся единых правил работы с Git, ветками, коммитами и Pull Request.

## Основной workflow

Основная ветка проекта — `main`.

Прямые коммиты в `main` не выполняются. Любые изменения вносятся через отдельную ветку и Pull Request.

Базовый workflow:

```text
main
 │
 ├── feature/...
 │       │
 │       └── изменения
 │              ↓
 │             PR
 │              ↓
 └─────────── main
```

Общий порядок работы:

1. Обновить локальную ветку `main`.
2. Создать новую ветку от актуального `main`.
3. Выполнить изменения.
4. Сделать коммиты.
5. Отправить ветку на GitHub.
6. Создать Pull Request в `main`.
7. Проверить изменения.
8. Выполнить merge.
9. Удалить рабочую ветку.
10. Обновить локальный `main`.

## Ветки

Для разных типов изменений используются разные префиксы.

### `feature/`

Используется для добавления новой функциональности.

```text
feature/user-authentication
feature/exam-practice
feature/progress-dashboard
```

### `fix/`

Используется для исправления ошибок.

```text
fix/login-validation
fix/task-result-calculation
```

### `docs/`

Используется для изменений документации.

```text
docs/project-documentation
docs/api-documentation
```

### `chore/`

Используется для технических изменений, которые не относятся непосредственно к функциональности приложения.

```text
chore/gitignore
chore/env-example
chore/update-dependencies
```

### `refactor/`

Используется для изменения существующего кода без изменения его поведения.

```text
refactor/task-service
refactor/authentication
```

## Создание новой ветки

Перед началом работы необходимо получить актуальное состояние `main`:

```bash
git switch main
git pull origin main
```

После этого создать рабочую ветку:

```bash
git switch -c <branch-name>
```

Например:

```bash
git switch -c feature/exam-practice
```

## Коммиты

Коммиты должны быть небольшими, понятными и описывать одно логическое изменение.

Используем формат:

```text
type: краткое описание
```

Например:

```text
feat: add exam task model
fix: correct score calculation
docs: update installation guide
refactor: simplify task service
chore: update dependencies
test: add task service tests
```

Основные типы:

| Type       | Назначение                                       |
| ---------- | ------------------------------------------------ |
| `feat`     | новая функциональность                           |
| `fix`      | исправление ошибки                               |
| `docs`     | документация                                     |
| `refactor` | изменение структуры кода без изменения поведения |
| `test`     | добавление или изменение тестов                  |
| `chore`    | технические изменения                            |

Не следует создавать коммиты с описаниями вроде:

```text
update
changes
fix
test
stuff
```

Описание должно позволять понять назначение изменения без просмотра всего diff.

## Pull Request

Каждое изменение, которое должно попасть в `main`, оформляется через Pull Request.

Название PR должно кратко описывать внесённые изменения.

Например:

```text
Add exam practice flow
Fix score calculation
Update project documentation
```

Перед созданием PR необходимо убедиться, что:

* изменения относятся к текущей задаче;
* в PR нет случайных файлов;
* код соответствует существующей структуре проекта;
* тесты проходят, если они уже существуют для соответствующей части проекта;
* документация обновлена, если изменения её затрагивают.

### Размер PR

Один PR должен содержать одну логическую группу связанных изменений.

Например, нормально объединить:

```text
README.md
CONTRIBUTING.md
.env.example
```

если они являются частью первоначальной настройки репозитория.

При этом не стоит объединять в один PR несвязанные изменения:

```text
добавление авторизации
+
исправление CSS
+
изменение README
+
обновление Docker
```

## Работа после merge

После успешного merge рабочая ветка больше не нужна и удаляется.

На GitHub ветку можно удалить через интерфейс Pull Request.

После этого локальный репозиторий необходимо синхронизировать:

```bash
git switch main
git pull origin main
```

При необходимости локальную ветку можно удалить:

```bash
git branch -d <branch-name>
```

## Общие правила

### Не коммитить секреты

Нельзя добавлять в Git:

```text
.env
```

пароли, API-ключи, токены и другие секретные данные.

Для описания необходимых переменных окружения используется:

```text
.env.example
```

---

### Не коммитить сгенерированные файлы

В репозиторий не должны попадать зависимости, кэши, временные файлы и другие автоматически создаваемые данные.

Например:

```text
node_modules/
.venv/
__pycache__/
```

Для этого используется `.gitignore`.

---

### Делать изменения небольшими

Предпочтительнее несколько небольших понятных изменений, чем один большой коммит или PR, содержащий множество несвязанных задач.

---

### Проверять изменения перед PR

Перед отправкой Pull Request рекомендуется проверить:

```bash
git status
git diff
```

А также запустить доступные тесты и проверки проекта.

---

## Вопросы и предложения

Если изменение затрагивает архитектуру проекта, структуру данных или ключевую функциональность, сначала стоит обсудить подход с участниками проекта.

Для небольших и очевидных изменений можно сразу создавать рабочую ветку и Pull Request.

## Краткая шпаргалка

```bash
# Обновить main
git switch main
git pull origin main

# Создать ветку
git switch -c feature/my-feature

# Работа над изменениями
...

# Проверить изменения
git status
git diff

# Создать коммит
git add .
git commit -m "feat: add my feature"

# Отправить ветку
git push -u origin feature/my-feature

# После merge
git switch main
git pull origin main

# Удалить локальную ветку
git branch -d feature/my-feature
```

Следуя этому workflow, мы сохраняем `main` стабильной и делаем историю проекта понятной для разработки и дальнейшего сопровождения.
